Built the round-phase state machine and role/disguise assignment - the
first slice of actual match gameplay (everything before this was menu/
lobby/settings plumbing). New files:
- jinzzaRoundTypes.h: EJinzzaRoundPhase (the 8 phases + RoundComplete),
  EJinzzaPartyRole (RealOne/Imitator/Judge), EJinzzaFaceType (A/B/C),
  EJinzzaVoiceFilter (High/Low/Robot) - shared enums used across the new
  classes below.
- jinzzaGameGameState.h/.cpp (AGameStateBase, now set as Lvl_Game's
  GameStateClass): replicates CurrentPhase (RepNotify -> OnPhaseChanged
  delegate, mirroring the AFruitGameState pattern the reference doc called
  out) and PhaseEndServerTime (a single timestamp against
  GetServerWorldTimeSeconds(), not a ticking countdown - the standard
  low-bandwidth technique) plus MidEvaluationsRemaining.
- jinzzaRoundPhaseSubsystem.h/.cpp (UGameInstanceSubsystem, matches the
  design doc's class list section 11 exactly): server-only phase driver.
  StartRound()/AdvancePhase() walk the 8 phases with an FTimerHandle,
  writing each transition into AjinzzaGameGameState. Two things aren't
  fully spec'd in the doc and needed a judgment call, both commented in the
  code:
    - Mid-evaluation looping for VoteCount > 1 (design doc section 17 lists
      this as still-undecided): implemented as repeating MidEvaluation ->
      FreeTime2 as a pair VoteCount times before Interview. VoteCount=1
      collapses to exactly the doc's worked 6-player timing example.
    - PhaseSpeed (Slow/Normal/Fast) multipliers aren't numbered in the doc;
      used 1.3x/1x/0.75x, applied only to FreeTime1/FreeTime2/Interview per
      the doc's own description of what that preset scales ("자유시간·면담
      시간 일괄 비율 조정"). Tune from playtesting per section 17.
  Question-time cycle count is hardcoded to the doc's default of 2 (130s)
  - not wired to a lobby setting yet, there isn't one for it in
  FJinzzaMatchSettings.
- jinzzaPartyPlayerState.h/.cpp (APlayerState, set as both Lvl_Lobby's and
  Lvl_Game's PlayerStateClass): holds bIsGhost/FaceType/VoiceFilter as
  openly-replicated properties (they're visible/audible in-game anyway) but
  deliberately does NOT replicate the player's Role - that's the doc's core
  "정보 비대칭이 곧 서스펜스다" principle (the Judge must not be able to
  infer anything from replicated data). Role only ever exists server-side;
  see below for how each client learns their own role.
- jinzzaDisguiseComponent.h/.cpp (UActorComponent, added to AjinzzaCharacter
  so every character subclass gets one): applies FaceType to the
  third-person mesh (the one other players see - GetMesh() is already
  SetOwnerNoSee'd) via a dynamic material instance driving a "FaceIndex"
  scalar param. No MI_Face_A/B/C content exists yet (design doc section
  13-2), so this is a no-op until that material parameter exists - same
  "functional once content exists, harmless until then" pattern
  UjinzzaGameUserSettings already established for audio.
- AjinzzaGameGameMode (jinzzaGameGameMode.h/.cpp): now sets GameStateClass/
  PlayerStateClass to the new classes above, overrides StartPlay() to kick
  off UjinzzaRoundPhaseSubsystem::StartRound(), and implements AssignRoles()
  (Fisher-Yates shuffle of GameState->PlayerArray -> 1 Real One + 1 Judge +
  the rest Imitators; Imitators clone the Real One's FaceType/VoiceFilter).
  Also fixed DefaultPawnClass, which was still the bare ADefaultPawn from
  initial project generation (nobody had a mesh, so disguise had nothing to
  apply to) - now loads BP_FirstPersonCharacter. This is a real behavior
  change for anyone testing Lvl_Game: players now spawn as the actual
  character instead of a flying camera.
- AjinzzaGamePlayerController: added Client_ReceiveRoleAssignment (a Client
  Reliable RPC) + GetLocalRole()/GetKnownRealOne() - this is how role
  knowledge actually reaches each player: AssignRoles() sends the Real One
  "you're the Real One", each Imitator "you're an Imitator, here's who the
  Real One is" (an APlayerState* reference), and the Judge "you're the
  Judge" with nothing else - matching the reference doc's suggested shape
  (client RPCs for private per-player notifications) instead of trying to
  make replication itself conditionally hide data.
- AjinzzaLobbyGameMode: now also sets PlayerStateClass to
  AjinzzaPartyPlayerState, so seamless travel into Lvl_Game never has to
  worry about the carried-over PlayerState still being the base APlayerState.
- Deliberately NOT built (flagged as simplifications, not oversights):
  - 2-judge mode: AssignRoles() always assigns exactly 1 judge regardless

  - Voice filter isn't consumed anywhere yet - UVoiceDisguiseComponent/

DONE THIS SESSION (2026-09-01, round 4, by Claude) - multi-instance PIE
playtest of the 3-player flow, found and fixed a real role-assignment bug
=================================================================
- Set up 3-client PIE via ObjectTools.set_properties on the
  ULevelEditorPlaySettings CDO (playNetMode=PIE_ListenServer,
  playNumberOfClients=3, runUnderOneProcess=true) - the StartPIE MCP tool
  itself has no multi-client option, but it reads these same editor
  play-settings, so this is the same mechanism the editor's own "Number of
  Players" dropdown drives.
- Bug found: PIE'd directly into Lvl_Game with 3 clients. After all 3
  jinzzaPartyPlayerState actors existed in GameState->PlayerArray (checked
  via find_actors/get_properties), Logjinzza still showed "AssignRoles:
  need at least 3 players, got 1 - skipping role assignment" - logged
  earlier, before the other two clients had finished connecting.
  AjinzzaGameGameMode::StartPlay() called RoundPhase->StartRound()
  synchronously, which enters RoleAssignment and calls AssignRoles()
  immediately - racing every remote client's connection, not just a
  seamless-travel corner case. In every real match this would silently
  leave 2 of 3+ players with no role (this was exactly round 2's flagged-
  but-unverified concern - now confirmed real).
- Fix applied (jinzzaGameGameMode.h/.cpp): moved the StartRound() trigger
  out of StartPlay() (which now only binds OnServerPhaseEntered) and into
  a new PostLogin() override that (re)starts a 1.5s debounce timer
  (TryStartRound(), guarded by bRoundStarted) on every login - so the round
  starts once no new player has joined for a beat, rather than on a fixed
  head count that could hang forever if someone disconnects mid-travel.
  Didn't thread an "expected player count" from the lobby through
  GameInstance instead, since that's an extra cross-level plumbing path for
  a number (MaxPlayers is the room's configured *cap*, not who actually
  shows up) that a debounce achieves more simply and more robustly.
- [x] Re-verified after the user compiled (via Hot Reload, not Live Coding -
  LogModuleManager showed UnrealEditor-jinzza-3762.dll reloaded, UBT log
  showed jinzzaGameGameMode.cpp recompiled, "Result: Succeeded"). Re-ran the
  identical 3-client listen-server PIE test on Lvl_Game: confirmed all 3
  jinzzaPartyPlayerState actors present, and - unlike the pre-fix run at the
  same point in the same test - no "AssignRoles: need at least 3 players"
  warning was logged at all this time, on either PIE start or through the
