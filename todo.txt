  - not wired to a lobby setting yet, there isn't one for it in

  off UjinzzaRoundPhaseSubsystem::StartRound(), and implements AssignRoles()

- AjinzzaLobbyGameMode: now also sets PlayerStateClass to

DONE THIS SESSION (2026-09-01, round 4, by Claude) - multi-instance PIE
playtest of the 3-player flow, found and fixed a real role-assignment bug
=================================================================
- Set up 3-client PIE via ObjectTools.set_properties on the
  ULevelEditorPlaySettings CDO (playNetMode=PIE_ListenServer,
  playNumberOfClients=3, runUnderOneProcess=true) - the StartPIE MCP tool
  itself has no multi-client option, but it reads these same editor
  play-settings, so this is the same mechanism the editor's own "Number of
  Players" dropdown drives.
- Bug found: PIE'd directly into Lvl_Game with 3 clients. After all 3
  jinzzaPartyPlayerState actors existed in GameState->PlayerArray (checked
  via find_actors/get_properties), Logjinzza still showed "AssignRoles:
  need at least 3 players, got 1 - skipping role assignment" - logged
  earlier, before the other two clients had finished connecting.
  AjinzzaGameGameMode::StartPlay() called RoundPhase->StartRound()
  synchronously, which enters RoleAssignment and calls AssignRoles()
  immediately - racing every remote client's connection, not just a
  seamless-travel corner case. In every real match this would silently
  leave 2 of 3+ players with no role (this was exactly round 2's flagged-
  but-unverified concern - now confirmed real).
- Fix applied (jinzzaGameGameMode.h/.cpp): moved the StartRound() trigger
  out of StartPlay() (which now only binds OnServerPhaseEntered) and into
  a new PostLogin() override that (re)starts a 1.5s debounce timer
  (TryStartRound(), guarded by bRoundStarted) on every login - so the round
  starts once no new player has joined for a beat, rather than on a fixed
  head count that could hang forever if someone disconnects mid-travel.
  Didn't thread an "expected player count" from the lobby through
  GameInstance instead, since that's an extra cross-level plumbing path for
  a number (MaxPlayers is the room's configured *cap*, not who actually
  shows up) that a debounce achieves more simply and more robustly.
- [x] Re-verified after the user compiled (via Hot Reload, not Live Coding -
  LogModuleManager showed UnrealEditor-jinzza-3762.dll reloaded, UBT log
  showed jinzzaGameGameMode.cpp recompiled, "Result: Succeeded"). Re-ran the
  identical 3-client listen-server PIE test on Lvl_Game: confirmed all 3
  jinzzaPartyPlayerState actors present, and - unlike the pre-fix run at the
  same point in the same test - no "AssignRoles: need at least 3 players"
  warning was logged at all this time, on either PIE start or through the
  full 6s warmup. No new errors/asserts/fatals either. Couldn't get a
