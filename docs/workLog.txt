2026-08-23
--------------------------------------------------------------------------------
[DOCS] Read and parsed docs/gamestart.docx (initial design doc, Korean).
  - Summarized concept: 5 disguised candidates (1 real / 4 imitators, identical
    body mesh, randomized face A/B/C + voice filter) vs. 1 uninformed judge who
    must identify the real one. Win condition is inverted from typical
    hidden-role games: candidates want to BE pointed at by the judge, not avoid it.
  - Captured round structure (~10.5 min/round @ 6 players): role assign -> intro
    (spotlight, 20s/candidate) -> free time 1 -> Q&A (write/answer/discuss loop)
    -> mid-vote elimination -> free time 2 (+1:1 interview target pick) -> 1:1
    interview -> final vote/reveal.
  - Captured 4 map zones (lobby, intro stage, Q&A field, 1:1 interview room,
    vote/reveal stage), noise/comedy props (megaphone, bat, bell, airhorn,
    drum, whistle, confetti cannon, radio), 4-emote system (F-you/thumbs
    up/thumbs down/peace via radial menu or hotkeys 1-4), ghost (eliminated
    spectator) state rules, and lobby config options (4-12 players, judge count,
    role-assign method, vote count, phase-speed preset, etc.).
  - Captured feature checklist by system: networking/matchmaking (Steamworks,
    variable lobby size, server-authoritative phase timer), voice/text
    (proximity voice, real-time pitch-shift voice disguise, isolated 1:1 voice
    channel, simultaneous-submit text Q&A), character (shared skeletal mesh +
    face swap, emotes), UI/UX (lobby, role reveal, vote UI, ghost-mode UI,
    phase timer), game logic (auto role assignment, vote tally, ghost
    transition, role rotation across rounds), map/level (4 zones + teleport,
    audio/visual isolation for interview room).
  - Open items flagged in doc for future design passes: emote radial menu UI
    mockup, prop balance (range/cooldown) via playtesting rather than upfront
    spec, 2-judge mode voting/interview rules, "candidate vote" role-assignment
    flow details.

[PLAN] Walked through a proposed build order with the user, biggest technical
  risk first (see conversation / project plan): voice pitch-shift + proximity
  voice middleware (Vivox or similar) called out as the #1 unknown; recommended
  sequencing is core lobby/networking -> role assignment & phase state machine
  -> character disguise swap -> voice pipeline spike -> UI -> props/emotes ->
  Steamworks integration -> playtesting pass on timings/balance.
